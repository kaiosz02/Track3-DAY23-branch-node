Tối Ưu 1 • Phân Tách Lỗi

Chuẩn Hóa Error Model & Tách Biệt Route

State & Errors
❌ Trước Tối Ưu
Trộn lẫn giữa Business Route (User báo lỗi hệ thống) và Runtime Exception (Timeout, 503, Network down). Dẫn đến Classifier bị nhiễu và routing sai.
# Lỗi runtime bị gán bừa vào route state["route"] = "error" # Exception làm crash ngang graph
✅ Sau Tối Ưu
route="error" chỉ dùng cho ticket chẩn đoán. Các lỗi kỹ thuật được normalize vào các field chuyên biệt:
state["error_type"] = "timeout" state["retryable"] = True state["safe_error"] = "Dịch vụ tạm ngưng..." state["internal_error"] = repr(exc)
💡 Lợi Ích Trọng Tâm
Bảo mật thông tin: User và LLM không bao giờ nhận stack trace thô hay database credentials (safe_error), trong khi hệ thống nội bộ vẫn lưu trữ đầy đủ internal_error cho audit log.
Tối Ưu 2 • Đánh Giá Kết Quả

Evaluate 3 Trạng Thái & Short-Circuit Dead Letter

Retry Policy
⚡ Cơ Chế 3-Outcome Evaluation
Thay vì chỉ có 2 nhánh nhị phân, evaluate_node hỗ trợ 3 trạng thái phân định rõ ràng:
1. success → answer
Tool chạy hoàn tất, chuyển sang tạo câu trả lời.
2. needs_retry → retry loop
Lỗi tạm thời (Timeout, 429, 503) có khả năng phục hồi.
3. failed_permanently → dead_letter
Lỗi vĩnh viễn (401 Unauthorized, 404 Not Found, Validation).
🔍 Code Router Triển Khai
def route_after_evaluate(state: AgentState) -> str: res = state.get("evaluation_result") if res == "needs_retry": return "retry" if res == "failed_permanently": return "dead_letter" # Đi thẳng, không retry vô ích! return "answer"
🚀 Tiết kiệm Token & Thời gian: Bỏ qua hoàn toàn các vòng lặp retry vô nghĩa khi gặp lỗi không thể sửa bằng cách thử lại.
Tối Ưu 3 • An Toàn HITL

Đóng Băng Tham Số Risky & Chống Bơm Tham Số

Security & HITL
🛡️ Vấn Đề Lỗ Hổng Sau Approval
Trong các hệ thống kém an toàn: Sau khi con người bấm Duyệt lệnh Hoàn tiền 500k, LLM được gọi lại để tạo arguments gọi API → Có nguy cơ sinh nhầm thành 5,000k hoặc bị prompt injection thay đổi payload!
# Giải pháp: Đóng băng payload trước khi xin duyệt action_id = str(uuid.uuid4())[:8] state["action_id"] = action_id state["proposed_action"] = frozen_payload
✅ Luồng Thực Thi Đã Khóa Cố Định
1. risky_action_node tạo action_id và đóng băng tham số.
2. approval_node kiểm tra Human Decision qua interrupt().
3. tool_node lấy trực tiếp payload đã duyệt để thực thi, tuyệt đối không gọi lại LLM để sinh tham số mới.
🔒 Tính toàn vẹn (Integrity): Những gì con người nhìn thấy và bấm duyệt là chính xác 100% những gì tool sẽ thực thi.
Tối Ưu 4 & 5 • Vận Hành Thực Tế

Idempotency Key & Exponential Backoff Retry

Reliability
🔑 Idempotency Key Chống Trùng Lặp
Khi thực hiện Refund hoặc gửi Email, nếu tool thành công nhưng mạng timeout ở bước trả lời → Graph retry sẽ không được thực hiện lại hành động lần thứ 2:
idempotency_key = f"{thread_id}:{action_id}" # Backend check: Nếu key đã execute, # trả kết quả cũ thay vì trừ tiền lần 2!
⏱️ Exponential Backoff Khi Retry
Tránh tình trạng dồn dập request (Thundering Herd) vào server đang nghẽn. Giãn cách thời gian chờ theo cấp số nhân:
delay = base_delay * (2 ** attempt) # Attempt 1: 0.25s # Attempt 2: 0.50s # Attempt 3: 1.00s time.sleep(delay)
Tối Ưu 6 • Lưu Trữ Phục Hồi

PostgreSQL Checkpointer (Supabase Pooler Integration)

Persistence
🐘 Cấu Trúc Bảng Checkpoint Supabase
Sử dụng langgraph-checkpoint-postgres kết nối qua Supabase Shared Pooler (IPv4):
• checkpoints: Lưu snapshot trạng thái mỗi node.
• checkpoint_writes: Lưu channel updates (messages, events).
• checkpoint_blobs: Lưu serialized payload.
• checkpoint_migrations: Quản lý version schema tự động.
# Cấu hình Pooler Transaction Mode tương thích: kwargs={"autocommit": True, "prepare_threshold": None}
⚡ Khả Năng Vận Hành Mang Lại
- Crash Resume: Tiến trình bị ngắt giữa chừng (hoặc chờ HITL) có thể resume lại chính xác từ node đã dừng.
- State History Audit: Dễ dàng truy vấn toàn bộ lịch sử biến thiên state bằng graph.get_state_history().
- Time Travel: Khả năng rollback hoặc thay đổi giá trị state ở một checkpoint trong quá khứ để chạy lại.
